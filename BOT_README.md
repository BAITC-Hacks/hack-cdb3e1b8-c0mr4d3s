# Telegram-бот HackAlem AI

## Что делать участнику, который отвечает за бота

Интеграция уже реализована: Telegram `/run` → `bot_eval.run_demo(42)` → агент участника 1 → штатный скоринг → отчёт и SQLite.

1. Один раз впишите полный токен BotFather в `.env`: `TELEGRAM_BOT_TOKEN=...`.
2. Запустите `start_bot.cmd` двойным щелчком. Окно должно оставаться открытым, пока идёт демонстрация.
3. В окне появится ссылка на вашего Telegram-бота. Откройте её и отправьте `/start`.
4. Нажмите `/run`, дождитесь отчёта, затем покажите `/last` и `/history`.

Это и есть демонстрация вашей части. Gemini используется внутри агента для выбора порядка гипотез перед пилотами. Ключ Gemini находится в `config.json`; отдельного Telegram-чата с Gemini создавать не нужно. Рассылки клиентам оператора бот не отправляет: расчёт работает на тестовых данных кейса.

Сообщение для передачи команде: «Бот вызывает `run_demo(42)`, показывает метрики и кампании, сохраняет результаты и ошибки в SQLite. Готовы `/run`, `/last`, `/history`. Сейчас используется `bot_eval.py`; после готовности вашего `demo_eval.py` переключим `bot.runner_module` в конфиге».

## Как устроен запуск

По умолчанию `/run` запускает **настоящий `Agent.act(env)` на локальной мок-среде организатора**. Пилоты и финальные кампании оценивает неизменённый `scoring_core.py`. Это локальная оценка, не прогноз результата на судействе. Отдельный режим `mock` возвращает фиксированные демонстрационные цифры без агента.

## Быстрый запуск в PowerShell

Откройте терминал в папке `hack-cdb3e1b8-c0mr4d3s`. В текущем окружении зависимости уже установлены. Для новой машины сначала выполните:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

В `.env` рядом с `bot.py` задайте токен своего бота от [@BotFather](https://t.me/BotFather):

```dotenv
TELEGRAM_BOT_TOKEN=ваш_токен
```

Файл `.env` загружается автоматически; токен из окружения терминала имеет приоритет. Читается только `TELEGRAM_BOT_TOKEN`. Остальные параметры приложения и ключ Gemini находятся в приватном `config.json`. Оба файла исключены из Git. Это сохраняет первоначальное соглашение команды о токене в переменной окружения.

```powershell
.\.venv\Scripts\python.exe bot.py --check-config
.\.venv\Scripts\python.exe bot.py
```

Первая команда проверяет настройки и наличие токена, не выводит его и не обращается к Telegram. Вторая запускает polling. Остановка — `Ctrl+C`. Запускайте один процесс на один токен и одну базу. Накопленные старые команды при старте отбрасываются. Публичный сервер или webhook не нужны.

При обычном запуске бот сначала проверяет токен через Telegram `getMe`. Отдельная проверка без запуска polling:

```powershell
.\.venv\Scripts\python.exe bot.py --check-telegram
```

Если Telegram отклонил токен (`InvalidToken` / `Unauthorized`), получите новый у [@BotFather](https://t.me/BotFather): `/mybots` → ваш бот → **API Token**. Если старый токен попал в сообщение или лог, отзовите его через **Revoke current token**, затем скопируйте новый в `.env`. Сохраните файл и снова откройте `start_bot.cmd`. В строке `TELEGRAM_BOT_TOKEN=...` должно быть только значение токена, без текста ответа BotFather. Ключ Gemini менять для этой ошибки не нужно.

Токен из окружения терминала имеет приоритет над `.env`. Если ранее задавали его в PowerShell, удалите старое значение командой `Remove-Item Env:TELEGRAM_BOT_TOKEN -ErrorAction SilentlyContinue` перед запуском, чтобы использовать `.env`.

## Конфигурация

Для новой установки скопируйте `config.example.json` в `config.json`, если у вас ещё нет личного конфига. Полный пример с включённым Gemini приведён в [README.md](README.md#конфигурация). Ниже — сокращённый пример без LLM; не заменяйте им уже заполненный личный файл. В существующий файл достаточно добавить секцию `bot`, сохранив ключ и параметры участника 1:

```json
{
  "bot": {
    "backend": "real",
    "runner_module": "bot_eval",
    "db_path": "bot_data/runs.sqlite3"
  },
  "gemini": {
    "enabled": false,
    "api_key": ""
  },
  "logging": {
    "level": "INFO"
  }
}
```

| Настройка | Назначение |
|---|---|
| `bot.backend` | `real`: вычисление через `run_demo`; `mock`: фиксированный ответ. |
| `bot.runner_module` | `bot_eval` сейчас; `demo_eval`, когда участник 2 предоставит свою функцию. |
| `bot.db_path` | SQLite. Относительный путь считается от папки `bot.py`. |
| `gemini.enabled` | `false` для воспроизводимого локального запуска без LLM API. |
| `gemini.api_key` | Ключ Gemini при включённой модели; не нужен Telegram-боту. |

Если JSON отсутствует или часть полей пропущена, используются эти значения по умолчанию. Настройки стратегии агента по-прежнему задаются в секциях `history` и `strategy`. После изменения настроек бота перезапустите процесс. `--backend` и `--db` переопределяют соответствующие поля на один запуск. Прежние `BOT_BACKEND` и `BOT_DB_PATH` больше не читаются: настройки объединены с конфигурацией участника 1 в JSON.

## Проверка без Telegram

Реальный агент, пилоты, штатный скоринг и запись в SQLite, без отправки сообщений:

```powershell
.\.venv\Scripts\python.exe bot.py --once
```

Прежний фиксированный мок, независимо от режима в конфиге:

```powershell
.\.venv\Scripts\python.exe bot.py --demo
```

Для polling с фиксированными цифрами: `.\.venv\Scripts\python.exe bot.py --backend mock`. Офлайн-записи используют `chat_id=0` и не попадают в историю Telegram-чатов. `--once` может обращаться к Gemini, только если вы включили его в конфиге.

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -v
```

Тесты проверяют команды, ошибки, SQLite, конкурирующие запросы, загрузку настроек, настоящий агент и совпадение метрик с `local_eval.evaluate_agent`. Telegram и Gemini в тестах не вызываются.

## Сценарий демонстрации

1. `/start` — справка и режим.
2. `/run` — один вызов `run_demo(42)`; чистый результат, расходы, контакты, количество пилотов и финальные кампании.
3. `/last` — последний запуск этого чата, включая ошибку или состояние выполнения.
4. `/history` — последние пять запусков, новые сверху.
5. Перезапустите бот и повторите `/last`: результат сохранён.

Одновременно выполняется один `/run`; история остаётся доступной во время расчёта. Метрики включают пилоты: бот не вычитает расходы повторно. При падении агента адаптер сохраняет и оценивает уже проведённые пилоты, помечая запуск ошибкой.

SQLite хранит начало/окончание в UTC, chat ID, seed, режим, состояние, метрики, кампании, количество пилотов и ошибку. В группе история общая для участников, в личном чате доступна только его история. Прерванный остановкой процесса запуск при следующем старте получает состояние ошибки.

## Передача участнику 2

`bot_eval.py` — временный адаптер в части бота. Он создаёт среду через `make_mock_env`, один раз вызывает `Agent.act`, добавляет исполненные пилоты перед финальными кампаниями и передаёт всё в `scoring_core.score_campaigns`. Формула скоринга не копируется. Пути к CSV абсолютные и не зависят от терминала. `agent.py`, `local_eval.py`, `scoring_core.py` и `submission.csv` интеграция не изменяет.

Согласованный интерфейс остаётся прежним:

```python
run_demo(seed: int = 42) -> dict
# {
#   "seed": 42,
#   "campaigns": [...],  # только финальные кампании
#   "n_pilots": 12,
#   "metrics": {
#       "net_arpu_gain": ..., "total_cost": ...,
#       "total_contacts": ..., "status": "PASS"  # или FAIL
#   }
# }
```

Дополнительно можно вернуть строку `error`: бот сохранит её вместе с метриками исполненных пилотов. Исключение функции сохраняется как ошибка запуска. Отрицательная метрика или статус `FAIL` сами по себе исключением не считаются.

Когда готов `demo_eval.py`, положите его рядом и поменяйте только `bot.runner_module` на `demo_eval`. При ошибке импорта или исполнения бот не подменяет результат фиксированным моком.

Зависимости агента и бота закреплены в едином `requirements.txt`.
