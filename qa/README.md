Тесты и отчёты участника QA. Проверенный код команды: `main` на коммите
`83bd2cbb57277862a6c919d3683ebeed8745f8d3`, 23 сентября 2026.
Код агента, исходный скоринг и файлы других участников здесь не изменяются.

**Состояние: агент проверен; интеграция `run_demo`, Telegram и SQLite ожидает реализации.**
18 автоматических тестов прошли: 11 тестов самого QA-инструмента и 7 сценариев
устойчивости настоящего агента. Реальные API-прогоны и ограничения описаны в
[отчёте](GEMINI_TEST_REPORT.md); оставшаяся работа — в [чек-листе](CHECKLIST.md).

## Подготовка без слияния веток

`qa/tests` содержит тесты, а код приложения находится в `main`. Поэтому
`--project .` из одной только ветки `qa/tests` не подойдёт. Тесты можно запускать
по абсолютному пути против отдельной копии проекта. Это не меняет `main`.

Пример для PowerShell, начиная в корне локального репозитория с чистым рабочим деревом:

```powershell
git status
git fetch origin
git switch qa/tests
git pull --ff-only origin qa/tests
$qa = Join-Path (Get-Location).Path 'qa'
git worktree add --detach ..\beeline-qa-main origin/main
$project = (Resolve-Path ..\beeline-qa-main).Path
```

`worktree add` выполняется один раз; целевой каталог должен быть новым.
Если ветка уже есть локально, `switch` только выбирает её. Если рабочее дерево
нечистое, сначала разберитесь со своими изменениями; эти команды не предусматривают
их удаления. Для повторения именно опубликованного отчёта вместо `origin/main`
при создании копии укажите SHA выше. Свежий `origin/main` может содержать другой код.

В отдельной копии установите зависимости в её `.venv`:

```powershell
py -3.12 -m venv "$project\.venv"
$python = Join-Path $project '.venv\Scripts\python.exe'
& $python -m pip install -r "$project\requirements.txt"
& $python -m pip check
```

Проверены Python 3.12.14 и все 30 версий из `requirements.txt`, включая pandas
3.0.6, NumPy 2.5.3 и google-genai 2.25.0. README приложения описывает Python 3.14;
эта QA-проверка не подтверждает запуск на каждой версии Python.

Нужны `agent.py`, `config.py`, `llm.py`, `logging_config.py`, исходные
`local_eval.py`, `scoring_core.py`, `environment.py`, `mock_environment.py`,
`make_submission.py`, `customer_profile.csv` и каталог `data/`.

## Основные проверки без внешнего API

В новой копии без `config.json` Gemini по умолчанию отключён. Если конфигурация
уже есть, для обычного QA задайте `gemini.enabled: false`: `qa_check.py`
использует настоящую конфигурацию агента и сам не запрещает API-вызовы.
Ключи для приведённых ниже offline-тестов не нужны.

```powershell
$env:QA_PROJECT = $project
& $python -B -m unittest discover -s "$qa" -p 'test_qa_check.py' -v
& $python -B "$qa\test_agent_resilience.py" --project "$project"
& $python -B "$qa\qa_check.py" --project "$project" --runs 10 --report "$project\qa_report.json"
```

Первая команда проверяет тестовый инструмент на подставных реализациях; она
не заменяет проверку настоящего `demo_eval.py`. Вторая проверяет реальный агент:
отрицательные и нечисловые ответы пилотов, зависимость решений от наблюдений,
сбой одного пилота, маленький бюджет/охват, границы размера пилотов 10 и 200.
Уменьшенные ресурсы — сценарии устойчивости, а не новые требования кейса.

`qa_check.py --runs 10` выполняет seed 42 и 0–9, затем два экспорта seed 42
в отдельных процессах. Таймаут — 600 секунд на процесс, включая загрузку.
Сравниваются CSV после нормализации перевода строк в LF; `submission.csv`
не перезаписывается. Используются `local_eval.evaluate_agent`,
`make_submission.build_submission` и исходный `scoring_core`, своей формулы нет.

Проверяются 1–10 финальных кампаний, корректность тарифов/каналов, пилоты,
лимиты и воспроизводимость экспорта. Одинаковые финальные сегменты и зависимость
от обрезки общего бюджета/охвата считаются ошибками по договору команды.
Пересечения разных сегментов и обрезка одной кампании до 5000 контактов —
предупреждения; скоринг организаторов может допускать их.

Коды выхода `qa_check.py`: `1` — ошибка; `2` — доступные проверки прошли,
но покрытие неполное (`PARTIAL`). Пока тесты Telegram/SQLite не реализованы,
общего `PASS` нет. `metrics.status` из скоринга — отдельный статус экономического
результата; он не означает, что вся интеграция проверена.

## Проверка Gemini и его сбоев

```powershell
& $python -B "$qa\check_gemini.py" --project "$project" --mode offline --seeds 42 --report "$project\gemini_offline.json"
& $python -B "$qa\check_gemini.py" --project "$project" --mode timeout --seeds 42 --report "$project\gemini_timeout.json"
& $python -B "$qa\check_gemini.py" --project "$project" --mode invalid_json --seeds 42 --report "$project\gemini_json.json"
& $python -B "$qa\check_gemini.py" --project "$project" --mode invalid_ids --seeds 42 --report "$project\gemini_ids.json"
```

Эти четыре режима не отправляют запросы провайдеру. Скрипт показывает результаты;
равенство кампаний и метрик между fallback и offline нужно сравнить отдельно.
В опубликованном отчёте такое сравнение выполнено для всех трёх сбоев.

Для **отдельного live-запуска** нужен личный локальный `config.json` проекта:
`gemini.api_key`, `gemini.enabled: true`, модель и лимиты из конфигурации команды.
Настоящий ключ в Git не добавлять; проверить исключение через
`git -C "$project" check-ignore config.json`.

```powershell
& $python -B "$qa\check_gemini.py" --project "$project" --mode live --seeds 42 --report "$project\gemini_live.json"
```

Live-режим обращается к API и расходует его квоту. Результаты: `MODEL_USED`,
`FALLBACK`, `MODEL_NOT_CALLED`; offline даёт `OFFLINE`. Код выхода `1` — ошибка
агента, `2` в live-режиме — успешное применение модели не подтверждено,
`0` — выбранная проверка завершилась без этих ошибок. После первой неудачи
провайдера live-пакет останавливается. Не считать fallback успешным ответом API.

`check_gemini.py` и тесты устойчивости привязаны к адаптеру и структуре текущего
агента; после изменения его внутренних интерфейсов тесты могут потребовать правки.
Новые сырые отчёты содержат путь к проекту и должны быть просмотрены перед публикацией.

## Подключение run_demo и бота

Согласованный интерфейс:

```python
run_demo(seed: int = 42) -> dict
# seed, campaigns, n_pilots,
# metrics: net_arpu_gain, total_cost, total_contacts, status
```

Когда `demo_eval.py` появится в проверяемой копии, `qa_check.py` автоматически
вызовет настоящий `run_demo(42)`: проверит один вызов `Agent.act`, соответствие
кампаний и числа пилотов этому запуску, использование исходного скоринга,
равенство возвращённых метрик его результату и строгую JSON-сериализацию.
Проверка учёта пилотов сейчас основана на числе оценённых кампаний. Правильные
`explicit_ids` пилотов, seed создания среды и отсутствие подмены её состояния
ещё нужно проверить при интеграции с реальным модулем.

Бот вызывает только `run_demo`; агент не зависит от Telegram или SQLite.
Пока реальных модулей нет, их статус `NOT_TESTED`, а не успешная проверка.
После согласования владельца модуля QA тестирует его работу, не дублируя реализацию.
Сначала нужны моки Telegram API и временная SQLite, затем полный показ
`/run` → `/last` → `/history` в тестовом чате. Сценарии перечислены в чек-листе.

Перед окончательной сдачей из проверенной копии проекта отдельно выполнить
штатные команды `python local_eval.py`, `python local_eval.py --runs 10`,
`python make_submission.py` и проверить комплект необходимых агенту файлов.
Публикация тестов в `qa/tests` не является слиянием в `main` и не сдаёт CSV.
