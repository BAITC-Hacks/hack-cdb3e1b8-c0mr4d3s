# HackAlem AI · Тарифные кампании Beeline

Агент выбирает кампании по истории смен тарифов, проверяет гипотезы пилотами и возвращает до 10 финальных кампаний. Telegram-бот показывает работу этого же агента и сохраняет результаты в SQLite. Все запуски используют мок-среду кейса; сообщения абонентам не отправляются.

Эта версия объединяет приложение из `main` (`60879fb`) и проверки команды в ветке `qa/tests`. **Все тесты, инструменты QA и отчёты находятся в `tests/`.** Ветка `main` при подготовке решения не изменялась.

## Быстрый запуск

Проверено на Windows с Python 3.12.14. Из корня репозитория, PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -X utf8 local_eval.py
.\.venv\Scripts\python.exe -X utf8 local_eval.py --runs 10
.\.venv\Scripts\python.exe -X utf8 make_submission.py
```

Последняя команда создаёт корневой `submission.csv` из реального результата агента с `seed=42`. По умолчанию Gemini выключен: ключи и интернет для оценки не нужны. Установка зависимостей требует доступа к пакетам.

## Файлы для сдачи

| Файл | Назначение |
|---|---|
| `agent.py` | Совместимый импорт `from agent import Agent`; использует единственную реализацию в `scripts/agent.py` |
| `submission.csv` | 10 финальных кампаний, воспроизводимых командой `python make_submission.py` |
| `scripts/` | Реализация агента, настройки, среда, исходный скоринг, общий оценщик и отдельный бот |
| `data/` | Данные кейса; агент читает историю из `data/change_tariff.csv` |
| `requirements.txt` | Зафиксированные зависимости |
| `tests/` | Автоматические проверки, единый запуск QA и результаты |

**Передавайте весь комплект с `scripts/` и `data/`: один корневой agent.py без этих зависимостей недостаточен.** Агент не импортирует Telegram-бота и не использует SQLite. Для работы в среде организаторов ему нужны `agent.py`, `scripts/__init__.py`, `scripts/agent.py`, `scripts/config.py`, исторические данные и зависимости. Полный комплект включает также инструменты локальной демонстрации.

Корневые `local_eval.py` и `make_submission.py` обеспечивают привычные команды исходного комплекта. Существующие команды `python -m scripts.local_eval` и `python -m scripts.local_eval --submission` тоже работают; вторая пишет тот же CSV в `data/submission.csv`.

## Как принимает решения агент

1. Формирует сегменты по текущему тарифу и ARPU, исключает слишком малые и слишком большие аудитории.
2. По истории переходов оценивает перспективные целевые тарифы. Исторический прирост — предварительная оценка, а не обещанный эффект кампании.
3. По умолчанию проводит до 12 пилотов по 150 контактов. Обновляет оценки по результатам пилотов с учётом неопределённости.
4. Выбирает до 10 кампаний, учитывая уже потраченные на пилоты бюджет и контакты. Финальные сегменты не пересекаются.
5. При неудачных наблюдениях и сбоях необязательной модели использует предусмотренную локальную логику.

Формула оценки используется из `scripts/scoring_core.py`. Код скоринга и стратегия из проверенного `main` не изменены при объединении с QA.

## Общий интерфейс оценки

```python
from scripts.local_eval import run_demo

result = run_demo(seed=42)
# result: seed, campaigns, n_pilots, metrics; при ошибке агента также error
# metrics: net_arpu_gain, total_cost, total_contacts, status и подробности скоринга
```

Каждый вызов выполняет `Agent.act(env)` один раз и оценивает реальные пилоты вместе с финальными кампаниями. При ошибке агента проведённые пилоты остаются в расчёте. `/last` и `/history` читают SQLite и не запускают агента повторно.

Бот сохраняет четыре согласованные метрики. Дополнительный `roi` в полном результате скоринга может быть бесконечным при нулевых расходах; для JSON используется нормализованный ответ бота. Поле `bot.runner_module` больше не поддерживается. Старые корневой `demo_eval.py` и папка `qa/` удалены как относящиеся к прежней структуре.

## Проверки

Полный прогон:

```powershell
.\.venv\Scripts\python.exe -X utf8 tests/run_all_checks.py
```

Скрипт проверяет зависимости, запускает все тесты через стандартный unittest discovery, оценку на одном и десяти seed, строгую проверку лимитов на seed=42 и 0–9, воспроизводимость экспорта, обработку сбоев Gemini без сетевых вызовов и цепочку агента с SQLite. Логи и JSON сохраняются в новой папке `test_results/`; эта папка исключена из Git.

Только тесты:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -t . -v
```

Подробности покрытия и итоговый результат: [tests/README.md](tests/README.md), [tests/FINAL_QA_REPORT.md](tests/FINAL_QA_REPORT.md).

## Локальная демонстрация без Telegram

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.bot --once --backend real
```

Запускается настоящий агент на мок-среде, выводится отчёт, запись сохраняется в `data/bot/runs.sqlite3`. Токен не нужен. Режим `--demo` предназначен только для фиксированного иллюстративного ответа; он не проверяет агента.

## Telegram-бот

Укажите `TELEGRAM_BOT_TOKEN` в окружении или в локальном `.env`:

```text
TELEGRAM_BOT_TOKEN=<токен вашего бота>
```

Затем:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.bot --check-telegram
.\.venv\Scripts\python.exe -X utf8 -m scripts.bot --backend real
```

Также можно использовать `start_bot.cmd`. Для одного токена должен работать один polling-процесс. Бот остаётся доступным, пока запущен компьютер и процесс владельца.

| Команда | Действие |
|---|---|
| `/start` | Описание и команды |
| `/run` | Новый запуск с seed=42 и сохранение даты, кампаний, метрик, числа пилотов и ошибки |
| `/last` | Последний сохранённый запуск текущего чата |
| `/history` | Последние пять запусков текущего чата |

Фиксированный seed нужен для повторяемого показа; устойчивость проверяется отдельно на других seed. История хранится на машине, где работает бот. Получение кода из GitHub не переносит живую SQLite другого участника. Токены, `.env`, `config.json` и базы не коммитятся.

## Необязательный Gemini

Без `config.json` модель выключена. Пример настроек — `config.example.json`; все настройки приложения, кроме согласованного Telegram-токена, читаются из локального `config.json`.

Для финальной воспроизводимой сдачи оставьте `gemini.enabled=false`. Если включить Gemini, понадобится ключ, а порядок гипотез и CSV могут измениться. Ошибка модели не считается успешным API-вызовом: агент переходит к локальному отбору. Режимы проверки находятся в `tests/check_gemini.py`; внешний `live`-режим не входит в финальный автономный QA.

## Что означают результаты

На проверенной мок-среде при seed=42: чистый результат **+3 329 109,82**, расходы **52 876**, контакты **13 219**, **12 пилотов и 10 финальных кампаний**. Расходы и охват включают пилоты.

`PASS` скоринга означает положительный чистый результат. Это не прогноз балла на судействе: скрытые эффекты будут другими. Финальный QA проверяет механику, воспроизводимость, интерфейсы и устойчивость. Доставка сообщений через живой Telegram отдельно проверяется владельцем бота перед защитой.
